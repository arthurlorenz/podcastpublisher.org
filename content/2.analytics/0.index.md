---
title: Analytics
description: Set up tracked audio URLs, read the analytics dashboard, and understand what counts as a download.
---

**Podcast Publisher Analytics** is an optional module labeled **Alpha** in Drupal's podcast menu. It counts *download intents* for episode audio and adds analytics pages per podcast and per episode. It is not a listener count or a measure of how much audio someone played.

Download counts are stored in your Drupal database, and location lookup uses a local GeoLite2 database. Apps, devices and bots are recognized with local user agent lists. You manage this data as part of your own site, including its access, backups, and retention.

## 1. Install the GeoLite2 City database

The analytics module checks for this exact file when it is enabled:

```text
web/libraries/geolite2/GeoLite2-City.mmdb
```

If your web root is not `web`, use `libraries/geolite2/GeoLite2-City.mmdb` inside your web root. Without the file, Drupal refuses to enable the module with the message *GeoLite2 City Database must be downloaded to the libraries folder*.

The GeoLite2 data is published by MaxMind under the [GeoLite2 End User License Agreement](https://www.maxmind.com/en/geolite2/eula). Check that your use complies with it.

### Option A: Composer

Add a package repository for the database to your project's `composer.json`. Composer installs it as a Drupal library and extracts it to the path above, provided your `installer-paths` map `type:drupal-library` to `web/libraries/{$name}`, as the `drupal/recommended-project` template does.

```json
"repositories": [
    {
        "type": "package",
        "package": {
            "name": "podcast-publisher-analytics/geolite2",
            "version": "1.0.0",
            "type": "drupal-library",
            "dist": {
                "url": "https://cdn.jsdelivr.net/npm/geolite2-city@latest/GeoLite2-City.mmdb.gz",
                "type": "gzip"
            }
        }
    }
]
```

Keep your existing repositories, such as `https://packages.drupal.org/8`, in the same list. Then run:

```bash
composer require podcast-publisher-analytics/geolite2
```

### Option B: Manual download

Download the **GeoLite2 City** database in binary `.mmdb` format, either from your [MaxMind account](https://dev.maxmind.com/geoip/geolite2-free-geolocation-data/) or from the mirror used above. Then place it in the libraries directory:

```bash
mkdir -p web/libraries/geolite2
curl -L https://cdn.jsdelivr.net/npm/geolite2-city@latest/GeoLite2-City.mmdb.gz | gunzip > web/libraries/geolite2/GeoLite2-City.mmdb
```

A download from MaxMind arrives as a `.tar.gz` archive. Extract it and copy only `GeoLite2-City.mmdb` into the directory.

### Keep it current

MaxMind updates GeoLite2 regularly. To refresh the database, replace the file using the same method you installed it with. The module opens the file each time cron processes the tracking queue, so no cache clear is needed.

The database is used for location lookup. A private development IP may have no result; the module logs that lookup error while still storing the download intent.

## 2. Install the OPAWG user agent lists

The module identifies apps, devices and bots with the [user agent lists](https://github.com/opawg/user-agents-v2) of the Open Podcast Analytics Working Group. It checks for the list files in this directory when it is enabled:

```text
web/libraries/user-agents-v2/build/
```

Without them, Drupal refuses to enable the module with the message *The OPAWG user-agents-v2 library must be downloaded to the libraries folder*.

### Option A: Composer

Add a second package repository to your project's `composer.json`, next to the one for GeoLite2:

```json
{
    "type": "package",
    "package": {
        "name": "opawg/user-agents-v2",
        "version": "1.0.0",
        "type": "drupal-library",
        "dist": {
            "url": "https://github.com/opawg/user-agents-v2/archive/refs/heads/master.zip",
            "type": "zip"
        }
    }
}
```

Then run:

```bash
composer require opawg/user-agents-v2
```

### Option B: Manual download

```bash
mkdir -p web/libraries/user-agents-v2
curl -L https://github.com/opawg/user-agents-v2/archive/refs/heads/master.tar.gz | tar -xz --strip-components=1 -C web/libraries/user-agents-v2
```

### Keep them current

The lists gain new apps and bots regularly. Replace the directory using the same method you installed it with; with Composer, run `composer reinstall opawg/user-agents-v2` after `composer clear-cache`. User agents your site has seen before keep the app and device they were recognized with.

### Update from 1.0.0-alpha11 or earlier

Earlier releases shipped their own user agent list. Install the OPAWG lists **before** you run the database updates, so the update can add devices to the user agents your site already knows. Until the lists are installed, the status report shows an error, and apps, devices and bots are not recognized.

## 3. Enable the optional module

Use **Extend** in Drupal or run:

```bash
drush en podcast_publisher_analytics
```

The main `podcast_publisher` module must already be enabled. Enabling analytics alone does **not** switch the feed's audio URLs to tracked URLs.

## 4. Track feed audio URLs

1. Open **Structure → Views → Podcast Feed** (`/admin/structure/views/view/podcast_feed`).
2. Select the **Feed** display.
3. Under **Fields**, open **Podcast Episode: Audio File**. Choose the field that provides the enclosure URL, not the separate Mimetype or Filelength fields.
4. Set **Formatter** to **Download Tracker URL**. Leave **Source** as `feed` unless you use another source label.
5. Click **Apply**, then **Save** the View.

![The Podcast Feed audio field using the Download Tracker URL formatter](/images/analytics-formatter.png)

*The formatter replaces the enclosure's direct file URL with a tracking URL.*

Open a podcast feed and inspect an episode's `<enclosure>` URL. A tracked URL begins with your site's domain followed by `/podcast-publisher/feed/`. The URL redirects to the audio file when requested. If it still points directly to `/sites/default/files/`, check that you edited and saved the **Feed** display's audio URL field.

## 5. Process requests and read the report

The tracking endpoint queues requests. Run Drupal cron regularly so its `podcast_download_intent_tracker` queue worker processes them. The report is at **Podcasts → your podcast → Analytics**, with a path like `/admin/content/podcast/{podcast_id}/analytics`. Viewing it requires **Administer podcast episode settings** permission.

![The Podcast Analytics dashboard with the period form, summary cards, trend chart and episode table](/images/analytics-report.png)

*The dashboard for one podcast.*

- **Period:** Since publication, Today, Last 7, 30 or 90 days, or a custom range. **Group by** shows the trend per day, week or month; **Automatic** picks one from the length of the period.
- **Summary:** downloads in the period, the change from the previous period of the same length, and the episodes released in it.
- **Trend:** downloads over time as a chart. **View data table** shows the numbers.
- **Episodes:** downloads per episode in the period, and in each episode's first day, 7, 30 and 90 days. The first-days columns ignore the period, so you can compare episodes of different ages. Click an episode for its own analytics page.
- **Breakdowns:** apps, devices, sources and formats as pie charts, countries and cities as tables. Apps and devices show the top nine and sum up the rest as **Others**. Click a country to see its cities.

Apps and devices come from the OPAWG lists. A download in a browser counts for the web app that linked to it, such as a web player, when the lists know its referrer.

The analytics pages are Views (**Podcast Analytics** and **Podcast Analytics Downloads**), and the charts come from the [Charts](https://www.drupal.org/project/charts) module, which the analytics module installs. Change them like any other View.

For a local check, request the tracked enclosure URL with `GET`, run cron, and reload the report. A normal browser or podcast client request is useful for this check; recognized bots are excluded.

## What the number means

- A `HEAD` request, or a request without a user agent, does not enter the tracking queue.
- Known bots are excluded, recognized by the OPAWG user agent lists.
- Repeated requests from the same IP address and user agent for the same episode are counted at most once within 24 hours.
- A full file request counts. Partial byte-range requests count once roughly one minute of audio has been requested within those 24 hours.
- Downloads are stored as hourly totals per episode, app, source and location. IP addresses are not stored; the 24 hour window keeps only a hash of IP address and user agent, and expires.

The report counts qualifying requests to **tracked** URLs. Direct file links, cached downloads served without reaching Drupal, and listening behavior after a redirect are outside what this module measures. If a count remains at zero, use the [analytics checks](/site-building/troubleshooting#analytics-still-shows-zero).

## Optional settings

Add these to `settings.php`:

| Setting | Effect |
| --- | --- |
| `$settings['podcast_publisher_analytics_bot_list']` | Path to a bot list in the format of the [IAB/ABC International Spiders & Bots List](https://iabtechlab.com/software/iababc-international-spiders-and-bots-list/), such as its `exclude_current.txt`. Matching user agents count as bots. |
| `$settings['podcast_publisher_analytics_ip_exclude_list']` | Path to a file with one IP address or CIDR range per line, such as the list's `ip_exclude_current_cidr.txt`. Requests from these addresses count as bots. |
| `$settings['podcast_publisher_analytics_raw_retention']` | Number of days to keep every processed request in the `podcast_download_intent` table, for your own analysis. Older requests are deleted on cron. Without it, no requests are stored. |

The IAB/ABC list is licensed separately; the module does not ship it.
